# Technology Authority Spec

**A one-page responsibility model for continuous design governance.
Not a team. Not a board. Not a process framework.**

The Technology Authority Spec defines a *responsibility*: any engineering team
that owns technology solutions commits to *visiting* four aspects of each
solution at least once every quarter, and to keeping a single honest dashboard
that shows where those visits stand.

## Why

Design governance formats (design authorities, CoEs, OSPOs) all share one core
duty: maintaining proper governance over all architectural aspects of a team's
technology estate. This spec distills that duty to its minimum viable form.
Small enough to adopt in an afternoon, strict enough to be meaningful.

## What this is

- A **responsibility** that any team can adopt by forking this repo
- A **single dashboard file** per team, readable at a glance
- A **commitment**: act on the dashboard, or don't adopt the spec

## What this is not

- Not a team, committee, or org structure
- Not a methodology or process framework
- Not a tool requirement. Any format/tool is compliant if it honors the spec
- Not a status report for management theater. The dashboard exists to drive
  the owning team's action, not to be negotiated with

## Quick start

1. Read [SPEC.md](SPEC.md) — that is the whole contract (~1 page)
2. Copy `dashboard.md` into your team's repo
3. Fill in your solutions and dates
4. Act on your first red item

## Adoption & exit

Adoption is open: no permission, training, or tooling required.
Exit is equally open: **if your dashboard no longer drives action, delete it
and stop practicing the spec.** A practice with a zombie state is worse than
no practice at all.

## Contributing

This spec is versioned. Teams pin a version; the spec evolves via ordinary
pull requests. Proposals that add mandatory process, tooling, or meetings
face a very high bar — brevity is the feature.
